# Reconcile

Single-user check register PWA. FastAPI + Jinja2 + htmx + Alpine.js + SQLite (stdlib `sqlite3`, no ORM). Design spec: `docs/superpowers/specs/2026-10-18-reconcile-design.md`.

## Commands

- Tests: `uv run pytest`
- Dev server (prefix `uv run --env-file .env` to load an `ANTHROPIC_API_KEY` for statement reading): `uv run uvicorn app.main:app --reload --reload-dir app --reload-dir static --reload-dir templates --reload-include '*.css' --reload-include '*.js' --reload-include '*.html'`
- Release (prod is amd64, dev machine is arm64): `./deploy.sh [--patch-bump|--minor|--major|X.Y.Z]`. With no argument it bumps the patch number of the newest `X.Y.Z` tag on origin (read with `git ls-remote`, so local tags don't matter) and asks before going ahead; `--patch-bump` does the same without asking. It tags and pushes the tag, builds and pushes `docker.io/xadamz23/reconcile:<tag>` (no `:latest`), then SSHes to the server and runs `update-app.sh <tag>`. That script (a copy is in `scripts/`) rewrites the server's `docker-compose.yaml` with the tag and restarts. That compose file loads `/home/dockerapps/reconcile/.env` (`env_file`) for `ANTHROPIC_API_KEY`, and the script stops if `.env` is missing (an empty one runs the app without statement reading). The server runs its own copy, so re-copy it to `/home/dockerapps/reconcile/` whenever it changes. It doesn't run tests. The repo's `compose.yaml` is a generic `.env`-driven version the server doesn't use.
- Regenerate icons: `uv run --no-project --with resvg-py --with pillow python scripts/make_icons.py`

## Layout

- `app/repo.py`: **all SQL**. Routes never write SQL themselves. Text is trimmed in `TxnInput.__post_init__` / `clean_text`, which is the one place whitespace stripping happens.
- `app/money.py`: amounts are **signed integer cents** (negative = payment). Never use floats `parse_cents` caps them at `MAX_CENTS` ($9,999,999.99).
- One SQLite connection is shared by all requests. `deps.get_conn` holds `app.state.db_lock` for the whole request, so routes must get the connection only through `Depends(get_conn)`. The one exception is `POST /reconcile/statement`, which mustn't hold the lock while Claude reads (10 to 40 seconds), so it uses `deps.locked_conn(app)` around its database work after the read.
- `app/db.py`: migrations are an append-only list keyed by `PRAGMA user_version`. Add a new entry and never edit an old one. `migrate()` turns foreign keys off around each script (and runs `foreign_key_check` before committing), so a migration can rebuild a table (create new, copy, drop old, rename) without the drop firing `ON DELETE` actions. Migration 4 does this to `bills`.
- `app/assets.py`: hashes every file in `static/` at startup. Templates must reference assets via `static_url('path')`, which yields `?v=<hash>` URLs that are served `immutable`.
- `app/routes/`: one router per area. `deps.render()` injects `today`.
- `app/routes/overview.py`: the Overview at `/`, the desktop landing page (the register is at `/register`, and the PWA's `start_url` points there so phones still open on it). It shows balance less the bills still to add (from `bills.month_context`), a 90-day balance chart with a dashed projection to month end, money in and out by month, this month's bills and spending, and things worth a look. The charts are server-drawn: the SVG paths and percentage positions are computed in Python, and `app.js` only drives the hover/arrow-key readout from `data-points`. Old `/?q=…` register links redirect to `/register`.
- Reading a statement with Claude (Reconcile page, shown only when `ANTHROPIC_API_KEY` is set: `app.state.ai_enabled`). `app/statement_text.py` pulls the text out of a PDF locally with `pypdf`, keeps only the summary block and the three transaction sections (found by heading, never by page number, since page count varies), drops pages with no transactions (the bank's blank balancing form), and redacts every 8+ digit or masked number and the holder's name. Only that text goes to Claude. Only PDFs are accepted; one without those headings (a scan) is sent as is. `app/statement_ai.py` asks for the lines as printed (unsigned, with their section) via structured output, and applies the sign from the section in code. The result is stored as JSON in `settings` (`rec_statement`) with the draft, and `_clear_draft` removes it. `app/statement_match.py` (no AI) matches lines to the reconcile's open items one-to-one: check number + amount, then the same amount within 10 days (nearest first), then flags "Amount differs" near misses (never matches them). It also checks the lines against the statement's printed totals. The review card (`_statement_review.html`) is recomputed on every body render. On a wide screen it sits in a sticky column beside the list (`.rec-split`; the list column is its own `ledger` container, so its rows go to columns at 42rem), and on a phone it comes above the list. Tests use a fake reader (`app.state.read_statement`) and made-up statements; real statements never go in the repo.
- `app/routes/spending.py`: the Spending page (payments per payee for a calendar period). Its bars are plain CSS (a span sized by `--w`, set server-side), with no chart library.
- `app/routes/bills.py`: the Bills page (recurring monthly bills), reached from the phone tab bar and the desktop sidebar. Ticking a bill adds that month's transaction. `_bills_body.html` renders the bills twice: phone rows (`.bill-rows`, in Still to add / Done this month groups, each row showing the bill's schedule and a status pill, open rows only within `SOON_DAYS`) and, at 900px and up, `_bill_cards.html` (a month rail of dots linking to `#bill-card-<month>-<id>-<seq>`, then cards in Still to add / Done this month groups, as many 17.5rem cards per row as fit). Both post to the same endpoints and refresh `#bills-body`. A card's status pill and action sit at its foot so they line up across a row; the schedule line, pill text and date tile come from `bills._row`. Both layouts also show **Overdue from <last month>** at the top (last month's payments never added or marked, each with Dismiss, which marks it `skipped`) and **Coming up in <next month>** at the bottom (all of next month's payments in one date-ordered list, so bills can go in the register before they're due), with a payday rule (`.payday-rule`) before the first one due on or after `bills.mid_payday` (the 15th, or the Friday before a weekend). The rule is only a visual guide; nothing depends on it. Overdue only covers months from the `bills_overdue_from` setting on (seeded by migration 6), so months from before it existed never flood the page, and a bill created after a payment's date doesn't owe it. The Overview counts overdue amounts in Free after bills and lists them under things worth a look. On desktop only (`.cal-anchor`, shown in the 900px block), a Calendar button beside Add bill opens this month and next as stacked calendars (`bills._calendar`, server-rendered, weeks from Sunday) with the 15th and the last day marked as paydays and today outlined; it's a plain Alpine `open` toggle (Esc and clicking outside close it). Done cards (`.bill-card.is-done`: added, paid elsewhere, nothing due) are dimmed to half strength and desaturated so open bills stand out, back to full on hover, focus or `:target`; phone rows aren't dimmed.
- `app/routes/plan.py`: the Plan worksheet (what might come out before payday, taken off the register balance to show what's left; it replaced a Google Sheet). Desktop only: the Plan button between Calendar and Add bill on Bills (`.plan-link`, shown in the 900px block) is a link to `/plan` with `target="reconcile-plan"`, and `app.js` opens it as a 700px popup, or brings an open one to the front without reloading it (`window.open("", name)`, then navigates only a blank one). It's a standalone page (`plan.html`, not `base.html`) with its own `plan.css` and `plan.js`, no htmx or Alpine. Lines live in `plan_lines` (label, `amount_cents` NULL = not counted, note) and aren't linked to bills or transactions. `plan.js` keeps the list in memory and POSTs all of it as JSON on every change (debounced, `repo.save_plan` replaces the table), sends anything unsaved with `keepalive` on `pagehide`, refetches `/plan/balance` on window focus, and resizes the popup to fit its rows. Amounts use the same cash-register entry as the app.
- `templates/_*.html` are htmx partials. `_panel.html` (the form panel) is shared by the register, reconcile and Bills pages, and `_tabbar.html` (the mobile bottom bar) and `_masthead.html` (the header, fed by `deps.masthead_context()`) by those, Spending and the Overview (which drops the masthead totals with `no_totals`, since its tiles show them). `_payee_field.html` is the payee combobox shared by the transaction and bill forms. `templates/sw.js` is the service worker, rendered by `routes/pwa.py`.
- `_sidebar.html` is the desktop navigation (account, New transaction, every page, Export CSV, and the totals at the foot). Every page includes it before `main` with `active` set (and `new_url` where there's a form panel). It's `display: none` below 900px, and its New transaction is the first `[data-new-txn]` on the page, so the `n` shortcut uses it. The totals are rendered twice, `#totals` in the masthead (phones) and `#side-totals` in the sidebar (desktop), and refreshes swap both out of band via `_totals_oob.html`.

## Gotchas

- Asset hashes are computed at startup. Without the `--reload-include` flags (which need `watchfiles`, a dev dep), CSS/JS edits keep their old hash and the browser serves the old immutable copy.
- htmx `attributesToSettle` is set to `[]` in `base.html`. The default settle step copies `class`/`style` between same-id elements and breaks Alpine's `x-show`.
- After a save, routes return `HX-Reswap: none` plus `HX-Trigger: ledger-changed, panel-close`. `#ledger` (register), `#rec-body` (reconcile) and `#bills-body` (Bills) refetch themselves on `ledger-changed`. htmx still fires `afterSwap` on these responses, so `app.js` opens the panel only on GET.
- Running balance is a window function over the **whole** ledger, applied before filters, so filtered rows still show true balances.
- The register pages its rows (`PAGE_SIZE` in `routes/register.py`). `_ledger_rows.html` ends with a placeholder that loads the next page (a `before=<date>:<id>` cursor) when it scrolls into view. The refresh after a save sends `rows=<count loaded>` so the list keeps its place. htmx merges `hx-vals` from every ancestor, even with `hx-disinherit`, so next-page requests carry `rows` too. The route ignores it when there's a cursor.
- Every bill action (`/add`, `/remove`, `/mark`, `/unmark`, the sheet's GET) carries the `month` it's for, and `bills._target_month` allows only this month, next month, or last month while it can be overdue (400 otherwise). Card ids, tick ids, the toast's Undo and `is-just-added` all include the month, since a bill appears once per month on the page.
- Bills never post on their own. A transaction made from a bill stores `bill_id`, `bill_month` (`YYYY-MM`) and `bill_seq`, with a unique index on all three so a double tap can't add it twice. A bill with `times = 2` has two rows a month (seq 1 and 2, the second on `day2`). How a row's tick behaves depends on the bill: `ask = 1` (`amount_cents` may be NULL for "Varies", and `day` may be NULL when there's no usual day; with a day it has a due date and the sheet starts on it) or `sometimes = 1` (not due every month) opens a sheet (`_bill_add_form.html`) for the date, amount and check number, plus "Nothing due this month" when `sometimes`. `elsewhere = 1` (paid from another account) adds nothing: its tick marks it paid. Paid and nothing-due marks live in `bill_marks` (one per bill, month and seq), and a payment can have a mark or a transaction, never both. Those rows sort to the bottom, and other-account amounts stay out of "left to add". Otherwise a tick adds an ordinary unverified payment dated the bill's day in that month (a late day moves to the month's last day). Deleting the transaction makes the bill addable again, even from the register. Editing or removing a bill never changes its transactions. The tick only takes back an `unverified` transaction: once a reconcile has ticked or locked it, it stays.
- Row-repeated icons use `sprite()` once on the page plus `icon_ref()` per row (`_icons.html`), instead of a full inline SVG on every row.
- Statuses are `unverified` → `verified` → `reconciled`. `verified` only means "ticked on the in-progress reconcile": there is no verify control in the register or the form. Only the reconcile tick, `finish_statement` and `discard_draft` change status; `update_txn` never does. A new transaction added from the reconcile screen (`/txn/new?date=…&verified=1`) starts ticked. The opening balance (`is_opening=1`) is reconciled and can't be deleted.
- The in-progress reconcile (closing date + statement balance) is a draft in `settings` (`rec_end_date`, `rec_balance_cents`). Reconcile routes read it instead of taking form fields. Finishing clears it and unticks any `verified` items dated after the closing date; discarding clears it and unticks every `verified` item.
- Cleared balance for reconciling = all reconciled + verified items dated on or before the statement's closing date.
- CSRF: middleware in `app/main.py` rejects any non-GET request that a browser marks as cross-site (`Sec-Fetch-Site`, falling back to `Origin` vs `Host`). Auth is only Cloudflare Access, so this is the one thing stopping other sites from posting forms. Requests with neither header (curl, TestClient) are allowed.
- `scripts/import_register_csv.py` is stdlib-only (it runs on the prod host, not in the venv) and writes SQL directly, against `SCHEMA_VERSION`. Bump that constant and re-check its INSERT when adding a migration.
- The transaction amount input (`data-cents`) uses cash-register entry: digits fill from the right and there's no decimal key. The sign comes from the Payment/Deposit toggle. It's handled in `app.js`. The statement balance uses `data-cents="signed"`, where typing `-` flips the sign because the balance can be negative. Phone number pads have no minus key, so a negative statement balance needs a hardware keyboard or a paste. The opening balance stays a free-form decimal input.
- The register's search line is always on desktop and opens from the masthead's search icon on mobile. All / Payments / Deposits and Show reconciled sit in a tray behind its filter button. Show reconciled is off in the normal register and on while searching: `enter()` in `filterBar` (`app.js`) ticks it and refetches when you focus a search field or open the tray, and Esc or the masthead's X (which takes the phone search icon's place while searching) clears everything and leaves search. The server only ever sees the checkbox, so it still defaults to off, and any filter in the URL (including `show_reconciled=true`) reloads in search mode. The button's count and the chips under the bar show what differs from the search defaults, so "Reconciled hidden" counts and reconciled being on doesn't.
- The `n` shortcut clicks the first `[data-new-txn]`: the desktop New transaction button or the tab bar's +. One of them is always hidden, but `click()` still works. Off the register, the masthead's search icon (and the tab bar's + on pages without a panel, plus the Overview's New transaction button) link to `/register#search` and `/register#new`, which `app.js` acts on after the register loads and then strips from the URL.
- Offline: `sw.js` loads pages from the network first and saves a copy of each main page (`SAVED`, only with no query string and never a redirect, so an expired Cloudflare Access login isn't saved) in the unversioned `reconcile-pages` cache. With no connection, or when Cloudflare answers a page load with 502 or above (server or tunnel down; a 500 from the app is shown as is), it serves that copy with `<html data-saved-at>` and `data-offline="offline"|"down"`, and `app.js` then shows an "Offline" or "Can't reach the server" note (with "Saved …" under it and a Retry button) and cancels every htmx request and form submit (the page is read-only). A page that was never saved falls back to `/offline`, which shows the last totals `app.js` stored in `localStorage` (`reconcile:totals`). Add a new top-level page to `SAVED` if it should work offline.
- Nav links are boosted: `hx-boost="true"` sits on the tab bar, the sidebar's `.side-links` and New transaction link, and the masthead's search icon and Overview item (only there: forms and Export CSV are never boosted). A boosted link swaps in the new page's `body` without a reload, so anything `app.js` does once on load must also run after a boosted swap (`htmx:afterSettle` with `e.detail.boosted`, on `document.body` only, since the event also fires on every swapped-in child). That covers the body's page class, the Overview chart (`initCharts`) and the `#search`/`#new` hash (`actOnHash`, which keeps `history.state` because htmx marks its entries there). Alpine components that add window listeners must remove them in `destroy()` (see `menu`). A boosted load that fails (send error, error status, timeout, or any boosted link on a saved offline page) falls back to `location.assign`, so the offline path above still handles it. htmx history snapshots are off (`historyCacheSize: 0`, `refreshOnHistoryMiss`), so Back reloads instead of showing an old balance, and `app.js` clears old `htmx-history-cache` entries.
- Prefetch: on `touchstart`/`mousedown` on a boosted link, `app.js` sends an `X-Prefetch` request that `sw.js` keeps in memory, and the boosted request on release uses it. Each is used once, within `PREFETCH_MS` (5s), and any non-GET clears them all, so a page is never older than the tap that opened it. Don't use htmx's preload extension instead: it relies on `Cache-Control: max-age`, which would let the browser serve stale pages (and stale `#ledger` refetches after a save). Boosted responses for `SAVED` pages are saved for offline too. Playwright's `setOffline` fires a spurious `online` event during navigation, which trips `app.js`'s reload-on-online, so test the offline fallback by stopping the server instead.
- The viewport meta has `interactive-widget=resizes-content`: on Android the keyboard shrinks the page instead of covering it, so the fixed sheet ends above the keyboard and scrolls to the focused field. With Chrome's default (`resizes-visual`) it panned the view instead, cutting off the sheet's top with no way to scroll back. Fixed-bottom UI (the tab bar) hides while a text field has focus, or it would ride up on the keyboard. Dismissing the keyboard on Android leaves the field focused, so `app.js` blurs it when the page returns to full height.
- `html` has `overscroll-behavior-y: none`. Android Chrome's overscroll stretch otherwise stretches the whole viewport, fixed tab bar included. It also turns off pull-to-refresh. (`contain` on the root keeps the stretch, so it isn't enough.)
- Avoid the font's tabular figures (`tnum`): Schibsted Grotesk also makes `.` and `,` tabular-width, which looks broken.
- Phones and desktop must stay independent: everything desktop-only goes inside the `@media (min-width: 900px)` block (or is hidden by default and shown there), and phone screenshots should come out pixel-identical before and after a desktop change.
- At 900px and up every `main` is a CSS size container (`ledger`), and the ledger columns, filter bar and reconcile summary respond to `@container`, not the window. Size containment makes `main` the containing block for `position: fixed` descendants and its own stacking context, so put toasts, dialogs and other overlays outside `main`.

## Design

Dark glassmorphism, dark-only (no light mode), except the Plan window: a light, flat accountant's columnar pad (pale green ruled paper, red ink for money out, single rule over the subtotal and double rule under Left), chosen so its what-if numbers never read as the register's. It's light only, its tokens are in `plan.css`, and the glass rules below don't apply to it. Frosted glass surfaces over a fixed "aurora" (`.aurora` in `base.html`: near-black `#070814` with three blurred sapphire, cyan and indigo glows). Tokens are in `:root` in `static/css/app.css`. Sapphire accent (a `#1d4ed8` → `#0e7490` gradient) for actions and the current tab. Payment red (`--pay`) and deposit/verified green (`--dep`) carry meaning, so the accent never stands in for either, and the Payment/Deposit pills keep red/green instead of the accent. The accountant's double rule (`border: double`) still marks final totals and draws in when a reconciliation balances. Mobile uses two-line rows inside glass cards and a full-screen sheet. Every page shares a bottom tab bar, a 64px glass panel with 24px corners floating clear of the screen edges, sized to its tabs and centered (Register, Spending, a flat 34×46 accent-outline + capsule in a 50px column so it has clear space either side, Bills, Reconcile). On phones Search is an icon in the masthead beside the ⋯ menu, and the Overview is in that menu. The active tab is a soft white glass tile (icon and label, 16% white) with an `--accent-text` icon, matching atmos and watchlist, and the back arrows are desktop-only. At 900px and up the layout is a desktop app: a floating glass sidebar on the left (the tab bar's 24px-cornered panel turned on its side, the current page in a tinted glass pill with an accent outline and icon, so it doesn't read as a second New transaction button, the balance under the double rule at its foot), the masthead reduced to a page-title row with no glass, and every page using the full width beside the sidebar (up to `main`'s 88rem). The form is a drawer that slides in from the right over a scrim only while it's open (the page keeps its full width), and once the register itself is 48rem wide it switches to columns (Payment / Deposit / Balance). Shortcuts: `n` new, `/` search, `Esc` closes the form, or otherwise clears and closes search.

## UI Conventions

The glass component classes live in one block ("Glass components") near the top of `app.css`. Build surfaces from them instead of writing one-off backgrounds, borders or blurs:

- `.glass`: cards, panels, filter bar, segmented-control tracks. Combine with `.card` (margins and radius) and `.card-list` (clips rows) for a list card.
- `.glass-strong`: chrome (masthead, tab bar, form sheet/drawer, menus, suggestions). Add `.is-popover` for dropdowns over text (92% instead of 60%, so text underneath doesn't show through).
- `.glass-chip`: small badges (check numbers, the Bills page's Today).
- `.glass-input`: inputs, or a wrapper around one (`.amount-input`), which then gets the focus ring via `:focus-within`.
- `.accent`: primary buttons. Has its own `:disabled` look. The current tab and the on-switch reuse its gradient. The tab bar's + (`.tab-add`) is deliberately not `.accent`: it's an outline capsule so it isn't mistaken for the current-tab pill.
- `.btn-glass`: secondary buttons. Fills with the accent on hover.
- `.pill-group.glass` + `.pill-radio` labels (radio inside, visually hidden): radio groups (spending periods, Payment/Deposit). It scrolls sideways when too wide.
- `.seg` + `.pill-radio` labels: a full-width segmented control with square-ish corners (register kinds).
- `.toggle-switch`: a switch (a `role="switch"` checkbox then a `span` label), like Show reconciled and the bill form's Not due every month.
- `.glass-card`: hover lift for clickable grid cards. There are none yet, so don't use it on list rows.

Rules: write only the standard `backdrop-filter`, never `-webkit-backdrop-filter`. Don't put `backdrop-filter` on per-row elements (put it on the containing card), because it's costly on long lists. `body` has no background on purpose: it would paint over the aurora (`z-index: -1`), and `html` carries `--bg`. Keep text at `--text-faint` (#8a92ad) or brighter so it passes AA on glass. The form panel and suggestion list are deliberately more opaque than the other chrome because content sits right behind them. There's no CSS build step: the classes take effect as soon as `app.css` changes.
